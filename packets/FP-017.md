# FP-017 — First Admitted Evidence Record End-to-End

## Task

Prove the ForgePilot evidence/admission plumbing with one boring admitted evidence record and one boring rejected control record.

## Goal

Move from V1 governance-complete/evidence-empty to a mechanically queryable evidence population proof.

FP-017 answers one question:

> Can ForgePilot create, query, and mechanically report at least one admitted evidence record while excluding a rejected control record?

## Background

FP-META-034 showed that current SQLite evidence/admission tables exist but contain zero evidence records and zero admission events.

The next step must be empirical, not doctrinal.

The first records should use low-stakes evidence so pipeline behavior is tested without introducing a live model-trust or bridge-refactor judgment.

## Scope

Add:

```text
runs/FP-017/evidence-fixtures/
runs/FP-017/evidence-population-script.mjs
runs/FP-017/admission-distribution-after.json
runs/FP-017/admission-distribution-report.md
runs/FP-017/file-sqlite-parity-check.json
```

Update:

```text
docs/forgepilot-progress-checklist.md
```

Implementation code may be added only if required to support a reusable report script or test harness.

## Required Positive Case

Create one boring evidence record that is:

```text
validation_state: VALID
admission_state: ADMITTED
trust_tier: TIER_2_VERIFIED_ARTIFACT
```

The source file artifact and SQLite record must pass a parity check.

## Required Negative Case

Create one boring control evidence record that is:

```text
validation_state: INVALID
admission_state: REJECTED
```

The regenerated report must show that the rejected record does not contribute to the admitted count.

## Required Report Behavior

The generated report must show:

```text
ADMITTED >= 1
REJECTED >= 1
```

and must explicitly distinguish admitted from non-admitted evidence.

## Required Boundary

No manual claim may be treated as stronger than generated output.

If the generated output and written interpretation disagree, the generated output wins.

## Safety Requirements

This packet must not execute models, modify MCP bridge code, rank models, change model trust state, backfill historical evidence, migrate historical files, or claim global V1 admission strength.

## Non-Goals

This packet does not admit all historical evidence, implement full file-to-SQLite backfill, implement invalidation propagation, regenerate the full V1 report, or resume the MCP bridge refactor.

## Acceptance Criteria

1. At least one SQLite evidence record exists with `admission_state = ADMITTED`.
2. At least one SQLite evidence record exists with `admission_state = REJECTED`.
3. The admitted record references a committed boring file artifact.
4. The rejected control record references a committed boring file artifact.
5. A parity check proves source file metadata matches the SQLite records.
6. A generated distribution report shows the admitted and rejected counts.
7. The rejected record is excluded from admitted count.
8. Re-running the script produces the same distribution for FP-017 records or handles idempotence safely.
9. No manual claim is treated as stronger than generated output.
10. Final git status is clean after evidence is recorded.
