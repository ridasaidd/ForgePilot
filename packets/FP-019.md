# FP-019 — Evidence Record Admission Event Linkage

## Task

Resolve the admission-path fork found by FP-017 by allowing `evidence_records` to be targeted by `evidence_admission_events`.

## Goal

Ensure an admitted evidence record and an admission event can refer to the same target instead of representing disconnected admission concepts.

FP-019 answers one question:

> Can evidence records participate in the same event-sourced admission/invalidation path as classification and outcome observations?

## Background

FP-017 proved `evidence_records.admission_state` plumbing with one admitted record and one rejected control. It also found that `evidence_admission_events` could not target `evidence_records`, because the admission API only allowed `classification_observation` and `outcome_observation`.

This created a structural fork:

```text
evidence_records.admission_state
```

versus:

```text
evidence_admission_events
```

## Scope

Update the admission API so `evidence_record` is a valid admission target type and is validated against `evidence_records.evidence_id`.

Add tests proving:

- an evidence record can receive an admission event,
- a missing evidence record target is rejected,
- eligibility derivation works for an admitted evidence record,
- a rejected evidence-record admission does not become eligible,
- invalidation can defeat an evidence-record admission.

## Required Boundary

FP-019 must not silently treat `evidence_records.admission_state` and event-sourced admission as identical unless a corresponding event exists.

Reports must be able to distinguish:

```text
evidence-record field state
```

from:

```text
event-sourced admission state
```

## Safety Requirements

This packet must not backfill historical evidence, rewrite FP-017 records, change model trust state, execute models, alter MCP bridge code, or claim all evidence records are event-linked.

## Non-Goals

This packet does not implement full historical backfill, propagation reports, V1 dashboard UI, or model routing.

## Acceptance Criteria

1. `evidence_record` is a valid admission target type.
2. Target validation checks `evidence_records.evidence_id`.
3. Existing classification/outcome admission tests still pass.
4. New evidence-record admission tests pass.
5. Eligibility derivation works for `evidence_record` targets.
6. Rejected evidence-record admission remains ineligible.
7. Invalidation can defeat an evidence-record admission.
8. FP-017 limitation is resolved as `EVENT_LINKAGE_IMPLEMENTED_FOR_EVIDENCE_RECORDS`.
9. No historical evidence backfill is performed.
10. Final git status is clean after evidence is recorded.
